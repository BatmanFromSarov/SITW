## 1. Принцип разработки

SITW разрабатывается поэтапно: сначала надёжное ядро, затем локальный ИИ, память и адаптация, после этого — дополнительные системы и интерфейсы.

Приоритеты:

1. Сохранность данных и контекста.
2. Стабильность и предсказуемость.
3. Полноценная работа без обязательного облачного ИИ.
4. Проверяемость результатов каждого этапа.
5. Расширяемость без переписывания ядра.
6. Защита разработчика от бесконечных циклов исправлений.

Функция не считается готовой, пока она не реализована и не проверена.

### Проверенный шаг — 01.11.2026: выбор backend в CLI

`python app.py` и `python app.py --backend test` сохраняют прежний тестовый
ответ. `python app.py --backend ollama` использует существующий `OllamaBackend`
через `Assistant`. Значения по умолчанию: `--model qwen2.5:7b`, `--timeout 120`.
Модель должна быть непустой, тайм-аут — положительным конечным числом секунд;
параметры модели и тайм-аута применяются только к Ollama.

Проверено: `python -m unittest discover -s tests -v` — 40/40 успешно;
`git diff --check` — без ошибок. Тесты используют mock HTTP и временные базы.
Пользователь записывается до генерации, успешный ответ — после неё;
отказы не создают ложных ответов, история сохраняется между запусками.

Не проверены реальная генерация, оборудование, качество, производительность
и автономность. История и системные инструкции модели не передаются.
Тайм-аут относится к операциям сокета, а не ко всей генерации.
Этап 2 остаётся в процессе; TestBackend остаётся backend по умолчанию.

## 13. Правила перехода между этапами

1. Следующий этап начинается после выполнения критериев текущего этапа либо после явного документирования принятого исключения.
2. Не добавлять новые функции ценой потери стабильности.
3. Не переписывать работающие компоненты без обоснованной причины.
4. Перед изменением существующих данных создавать резервную копию.
5. После каждого существенного изменения запускать соответствующие тесты.
6. Не отмечать задачу выполненной без проверяемого результата.
7. Если задача блокируется, фиксировать причину и следующий конкретный шаг вместо повторения неудачных действий.
8. При изменении плана обновлять этот документ.
